# Монетизация «Рациона»

Система уже встроена в приложение. Владелец управляет ею на странице **«Монетизация»** (`/billing/admin`), пользователь видит **«Тариф и оплата»** (`/billing`). На телефоне эти разделы доступны из «Моей цели» через значок аккаунта.

После установки ограничения и продажи **выключены**. Существующие пользователи продолжают пользоваться приложением бесплатно, пока владелец сам не сохранит новые настройки. При перезапуске настройки сохраняются в PostgreSQL.

## Предлагаемая модель

| Вариант | Стартовые условия | Назначение |
| --- | --- | --- |
| Базовый | 3 создания меню в календарный месяц, бесплатно | Попробовать приложение и возвращаться к сохранённым неделям |
| Пробный доступ | 7 дней, 5 созданий на весь период, один раз на аккаунт | Проверить, подходит ли более частое составление меню |
| Плюс | 60 созданий в календарный месяц | Менять меню и экспериментировать с рецептами |
| Оплата Плюс | 299 ₽ за 30 дней или 2 490 ₽ за 365 дней | Разовая покупка доступа на выбранный срок |

Это стартовая гипотеза, а не обещание оптимальной цены. Все числа, названия и варианты оплаты редактируются в панели. Можно добавить до восьми вариантов, например 90 дней, скрыть отдельное предложение или временно остановить продажи.

Плата берётся за дополнительное создание меню. Цели питания, личные продукты и рецепты, чтение сохранённых меню, история и списки покупок не блокируются после окончания срока или исчерпания лимита. Рекламы и продажи пользовательских данных в модели нет.

Нет автоматических списаний, сохранения карты и автоматически платной пробы. Пользователь сам запускает пробу или выбирает разовую оплату. Повторная покупка продлевает доступ: новый период начнётся после последнего уже выданного периода. Число дней указано явно — «30 дней», а не календарная подписка на месяц.

## Как менять настройки

1. Откройте «Монетизация».
2. Задайте лимиты бесплатного и платного тарифа. Платный лимит должен быть больше бесплатного.
3. Настройте пробный период: разрешён ли он, сколько дней длится, сколько меню можно создать за всю пробу.
4. Укажите цены в рублях и длительность вариантов оплаты. Цена относится ко всему сроку, а не к одному месяцу.
5. Проверьте карточку «Предпросмотр». До нажатия «Сохранить настройки» пользователи ничего нового не увидят.
6. Для начала ограниченного теста включите только лимиты. Приём оплаты можно открыть отдельно после подключения магазина.

«Отменить мои изменения» возвращает сохранённую версию. «История настроек» позволяет перенести прежние значения в форму и сохранить их заново. Возврат также записывается в журнал. Одновременное редактирование в двух вкладках не перезаписывает чужие изменения: вторая вкладка получает сообщение о конфликте.

Изменение цен и платного лимита влияет на новые заказы. Уже созданный заказ сохраняет цену, число дней и лимит, даже если оплатить его позднее. Купленные и подарочные периоды, начатая проба сохраняют свои условия. Бесплатный тариф меняется сразу после сохранения. Выключение общего переключателя снимает ограничения, но не останавливает течение уже выданных периодов; выключение только продаж прекращает создание новых заказов. Ранее созданные заказы можно оплатить, проверить и вернуть независимо от переключателей.

## Лимиты без неприятных сюрпризов

- Одно успешно сохранённое меню — одно использование, независимо от числа дней в меню. Неудачная генерация и ошибка записи в базу лимит не расходуют.
- Бесплатный и платный тариф используют общий счётчик календарного месяца UTC. Он обновляется 1-го числа в 03:00 по Москве. При переходе с 3 на 60 уже использованные в этом месяце попытки учитываются. Остаток не переносится.
- У пробы отдельный счётчик на весь её срок; переход на новый месяц не даёт вторую пробную квоту. Оплата сразу заменяет пробный доступ; неиспользованные дни пробы не добавляются к покупке.
- Удаление меню не возвращает использование. Параллельные запросы с разных устройств или процессов сервера не позволяют превысить лимит.
- При отключённой монетизации новые использования не записываются; уже накопленный счётчик месяца сохраняется на случай повторного включения.
- Подарок выдаётся в панели по email существующего аккаунта. Укажите число дней и причину. Он получает платный лимит, действующий в момент выдачи, и фиксируется в журнале. Подарок можно отозвать; этот механизм не отменяет оплаченные периоды.
- Пробный период ограничен аккаунтом, а не человеком. Подтверждение email и антифрод для массового создания аккаунтов не входят в эту версию.

## Первый запуск для владельца

Нужны существующий аккаунт в приложении и обновлённая база. В корне монорепозитория:

```sh
npm run db:generate
npm run db:migrate
npm run build
npm run billing:admin -w @meal-planner/backend -- grant owner@example.com
```

В последней команде замените адрес на email своего зарегистрированного аккаунта. Команда не создаёт пользователя и не меняет другие роли. Обновите страницу приложения: появится «Монетизация». Отзыв доступа:

```sh
npm run billing:admin -w @meal-planner/backend -- revoke owner@example.com
```

Для Docker после пересборки и применения миграций:

```sh
docker compose up -d --build
docker compose exec backend npm run billing:admin -- grant owner@example.com
```

Миграция `20261003000000_billing` только добавляет таблицы и отдельное право управления монетизацией. Автоматического назначения владельца по номеру пользователя, email из запроса, общей роли admin или праву модерации отзывов нет. Не применяйте `migrate reset` к рабочей базе.

## Подключение ЮKassa: один раз на сервере

Локальный запуск читает `apps/backend/.env`, Docker — корневой `.env`. Существующие файлы не перезаписывайте. Ключи не вводятся в интерфейс приложения и не передаются пользователю.

| Поле | Значение |
| --- | --- |
| `BILLING_PAYMENT_MODE` | `disabled`, `test` или `live`; по умолчанию `disabled` |
| `YOOKASSA_SHOP_ID` | Идентификатор выбранного магазина |
| `YOOKASSA_SECRET_KEY` | Секретный ключ этого магазина |
| `BILLING_RETURN_URL` | Полный адрес страницы тарифов, например `https://your-domain.example/billing`; локально разрешён `http://localhost:3000/billing` |
| `YOOKASSA_RECEIPT_MODE` | `provider` — передавать чек с платежом; `external` — отправка чеков организована отдельно |
| `YOOKASSA_VAT_CODE` | Код вашей ставки для чека; обязателен в режиме `provider` |

Приложение не выбирает налоговый режим за владельца. Режим `provider` передаёт email покупателя, одну услугу, цену, код ставки, `payment_mode=full_payment` и `payment_subject=service`. Совместимость этих реквизитов и способа выдачи чеков с вашим магазином нужно настроить при подключении. Значения кодов — в [официальном справочнике ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/parameters-values). Режим `external` сам чеки не формирует.

В кабинете ЮKassa добавьте адрес **вашего API** `https://api.your-domain.example/billing/webhook/yookassa` и события:

- `payment.succeeded`;
- `payment.canceled`;
- `refund.succeeded`.

После изменения серверных переменных перезапустите backend. Сначала используйте тестовый магазин и `test`. В панели включите лимиты и приём оплат, сохраните, сделайте тестовую покупку и проверьте полный возврат. Тестовые заказы помечены, не входят в выручку и не дают платного доступа после переключения в `live`. Незавершённый тестовый заказ не блокирует покупку в боевом магазине.

Для настоящих оплат укажите реквизиты боевого магазина и `live`. Подготовка аккаунта магазина, фактическая тестовая оплата в ЮKassa и боевой запуск требуют ваших реквизитов; исходный код сам этого не делает. Секреты не нужно присылать в чат.

Панель проверяет заполненность подключения; она не обещает, что ключи действуют, пока не выполнен тестовый платёж. Поддержан один текущий магазин: перед его заменой закройте или сверяйте старые заказы с прежним подключением.

## Заказы, ошибки и возвраты

Стоимость определяется сервером. Пользователь подтверждает видимую цену и срок, затем переходит на страницу ЮKassa. Возвращение на страницу приложения само по себе не означает оплату: backend повторно запрашивает состояние платежа. Проверяются сумма в копейках, рубли, магазин, режим test/live, номер заказа, номер платежа и фактический статус.

Один аккаунт может иметь один незавершённый заказ в текущем магазине и режиме. Кнопка «Проверить статус» обновляет сведения, «Продолжить оплату» открывает уже созданный платёж. Повторный запрос использует прежний идентификатор и неизменное тело запроса. Если магазин временно не ответил, проверяйте существующий заказ; не создавайте вместо него новое списание.

Владелец видит последние заказы и может искать по email. Возврат оформляется в кабинете ЮKassa. Проверенное уведомление о полном возврате отзывает только период этого заказа; частичный возврат отражается в сумме и сохраняет доступ. При возврате предыдущего периода даты уже купленных последующих периодов не сдвигаются. Платёжные события могут повторяться и приходить в разном порядке — повторного продления и восстановления возвращённого периода не происходит.

Если уведомление потерялось, можно проверить отдельный заказ в панели либо сверить все ожидающие и оплаченные заказы текущего подключения:

```sh
npm run billing:reconcile -w @meal-planner/backend
# Docker:
docker compose exec backend npm run billing:reconcile
```

Эту команду можно подключить к вашему серверному расписанию. Она работает последовательно, небольшими порциями, и возвращает ненулевой код при ошибках. Расписание автоматически не создаётся. Сумма в отчёте — реальные подтверждённые оплаты за вычетом проверенных возвратов, без комиссии сервиса, налогов, тестовых оплат и подарков.

ЮKassa хранит ключ идемпотентности 24 часа. Поэтому неизвестный результат создания заказа старше 23 часов не отправляется повторно. Если у заказа нет номера платежа, найдите платёж в кабинете магазина по номеру заказа из `metadata.order_id` и нажмите «Найти платёж» у заказа в панели владельца. Укажите идентификатор платежа ЮKassa. Для интеграций доступен также защищённый API `POST /billing/admin/orders/:id/link` с `{ "paymentId": "номер платежа ЮKassa" }`. Сервер сам запросит и проверит платёж; вручную отметить произвольный заказ оплаченным нельзя. Если платежа нет, нужно сначала разобраться с исходным запросом у провайдера; система намеренно не делает новое списание автоматически.

Протокол интеграции: [создание платежа](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process), [уведомления](https://yookassa.ru/developers/using-api/webhooks), [идемпотентность](https://yookassa.ru/developers/using-api/interaction-format).

## Что смотреть после запуска

Начните с одного понятного предложения. Через несколько недель сравните, сколько людей попробовали сервис, сколько купили доступ, пользуются ли им повторно и что пишут в обращениях. Меняйте по одному параметру — например цену или бесплатный лимит — и фиксируйте дату в истории. Текущая панель показывает выручку, активный оплаченный доступ, число успешных платежей и незавершённых проб; подробной событийной воронки и автоматических экспериментов пока нет.

Система не включает автопродление, промокоды, рекламные сети, подарочные сертификаты на продажу, другие валюты и провайдеров. Платёжный провайдер отделён интерфейсом `PaymentGateway`, поэтому следующий способ оплаты можно добавить без изменения расчёта лимитов и тарифов.

## Проверки разработки

`npm run check` — линтер, типы, модульные тесты и сборка. `npm run test:integration` — HTTP и настоящая временная PostgreSQL-база. Сценарии монетизации проверяют права, гонки настроек и лимитов, атомарность списания, пробу, неизменность цены, повторные запросы, ложные параметры платежа, приватность заказов, продление, возвраты и проверку уведомлений. Ответы платёжного сервиса в автоматических тестах моделируются, реальные деньги не списываются.
