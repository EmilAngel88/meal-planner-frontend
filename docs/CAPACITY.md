# Многопользовательская работа и нагрузка

## Что изменено

Самое тяжёлое действие — подбор меню — раньше выполнялось синхронно внутри HTTP-процесса. Пока рассчитывались дни, остальные пользователи ждали даже простые ответы. Теперь расчёт выполняется в переиспользуемых `worker_threads`; базу читает и записывает только API. Алгоритм, округление порций и формат сохранённого меню сохранены.

- На один API-процесс: 2 вычислителя, максимум 4 ожидающих расчёта, до 45 секунд на очередь и расчёт вместе. Переполнение возвращает понятный `503` и `Retry-After`, повторная параллельная генерация одного аккаунта — `429`. Разрыв соединения отменяет ожидающий/работающий расчёт. На каждый вычислитель установлен лимит old-generation heap 256 MB; это не предел полного RSS процесса.
- Общая обработка API ограничена 256 одновременными запросами. Лимит включён до чтения JSON. Проверки `/live`, `/ready`, `/health` доступны отдельно. Заголовки, чтение тела и простаивающие соединения имеют таймауты.
- Один Prisma-клиент на API-процесс, по умолчанию до 10 соединений. Ожидание соединения 5 секунд, соединение с БД 5 секунд, ожидание ответа БД 30 секунд. Явные параметры в `DATABASE_URL` имеют приоритет. Вычислители не создают свои пулы и не получают окружение с секретами.
- Индексы для пользовательских списков, истории веса, ингредиентов, коллекций и позиций меню. Нормализация поиска продуктов работает и в БД с `C` locale. Миграция только добавляет функцию/индексы; старые данные не удаляются.
- Каталоги и настройки выдаются страницами. `/menu/settings?limit=200&offset=0` возвращает прежние массивы и `hasMore`; offset применяется к общему списку рецептов до разделения на базовые/личные. В настройках нет тяжёлых вложенных ингредиентов. История `/menu?limit=20&offset=0` по умолчанию содержит 20 меню, максимально 50. Сохранённые записи не ограничены искусственной квотой.
- За один расчёт загружаются только базовые и выбранные/включённые личные рецепты, до 500 суммарно. При превышении возвращается `422` с просьбой уменьшить выбор, без молчаливого отбрасывания рецептов. Снимки покупок сохраняются как прежде.
- При `SIGTERM` готовность снимается, API завершает активные запросы, закрывает вычислители и соединения с БД. Предельное ожидание 30 секунд; Docker даёт 35 секунд перед принудительным завершением.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `GENERATION_WORKERS` | 2 | Одновременные расчёты на API-процесс, диапазон 1–8 |
| `GENERATION_QUEUE_LIMIT` | 4 | Максимум ожидающих расчётов, диапазон 0–100 |
| `GENERATION_TIMEOUT_MS` | 45000 | Общий срок расчёта с очередью |
| `MAX_CONCURRENT_REQUESTS` | 256 | Активные обычные запросы на процесс |
| `SHUTDOWN_TIMEOUT_MS` | 30000 | Максимальное время завершения API |
| `DATABASE_CONNECTION_LIMIT` | 10 | Размер пула в Docker Compose; локально задаётся `connection_limit` в URL |
| `TRUST_PROXY` | пусто | Адреса/CIDR прокси, которым разрешено передавать IP пользователя |

За reverse proxy укажите только его реальный адрес/подсеть и закройте обходной прямой доступ к API. Значения `true` и числовое число hops не принимаются: произвольный `X-Forwarded-For` не должен позволять обходить защиту входа. Прокси должен иметь timeout больше 60 секунд для генерации. CORS не заменяет аутентификацию.

При `NODE_ENV=production` сервер отказывается запускаться с `JWT_SECRET` короче 32 байт или известным значением-заглушкой из примера. Используйте случайный секрет: длина сама по себе не гарантирует его непредсказуемость. `scripts/init-docker-env.cjs` создаёт случайные секреты для нового Docker-окружения. Реальные `.env` и текущие пользовательские токены этой доработкой не меняются; локальная разработка сохраняет совместимость с существующим секретом.

Число соединений с PostgreSQL планируется **суммарно**: число API-процессов × размер пула, плюс миграции, мониторинг и административный запас. Увеличение числа вычислителей без свободных CPU/памяти ухудшает задержки. Увеличение очереди увеличивает ожидание, а не производительность.

## Воспроизводимая проверка

Нужны установленный Node.js поддерживаемой проектом версии, зависимости и отдельный PostgreSQL с правом `CREATE DATABASE`/`DROP DATABASE`. Запуск из корня:

```sh
TEST_DATABASE_URL=postgresql://test_user:test_password@127.0.0.1:5432/postgres npm run test:capacity -w @meal-planner/backend
```

Скрипт требует явно заданный `TEST_DATABASE_URL`. Он создаёт случайно названную БД `meal_planner_capacity_<pid>_<timestamp>`, применяет миграции, заполняет каталог и 300 тестовых аккаунтов, запускает собранный API на временном локальном порту и удаляет только эту БД в `finally`. Рабочая БД не сбрасывается. При принудительном убийстве всего тестового процесса временная БД может остаться; её имя видно среди БД сервера, удалять следует только подтверждённую тестовую БД.

Проверяются 1200 чтений с 50 одновременными запросами от 300 аккаунтов и параллельная серия из 10 генераций по шесть дней. Скрипт проверяет отсутствие чужих продуктов/профилей, успешное чтение, управляемое отклонение избытка генераций, последующую готовность API и успешное завершение по `SIGTERM`. Тест не моделирует 300 одновременных расчётов и не включает браузер/сеть/внешний прокси. JWT выдаются тестовым аккаунтам напрямую; стоимость хеширования паролей при входе/регистрации здесь не измеряется.

Локальный результат 29.09.2026, Node 24.8.0 / PostgreSQL 14, сборка production, один API:

| Проверка | Результат |
| --- | ---: |
| Аккаунтов / параллельных чтений | 300 / 50 |
| Чтений / ошибок чтения | 1200 / 0 |
| Время чтений | 1074 мс |
| Пропускная способность чтений | 1117 запросов/с |
| p50 / p95 / максимум | 41 / 71 / 263 мс |
| Серия генераций | 6 × `201`, 4 × ожидаемый `503` |
| Соединений БД с учётом fixture-клиента | 11 |
| Готовность после нагрузки / штатное завершение | `200` / код 0 |

Это короткий локальный smoke-тест, **не гарантия мощности production**. Сотни зарегистрированных пользователей и сотни одновременно выполняющих расчёт пользователей — разные нагрузки. Перед запуском на целевом сервере повторите проверку через production-подобный прокси с реальными размерами каталога, а затем продолжительный тест своего ожидаемого поведения. Следите за p95, ошибками `5xx/429`, очередью вычислений, CPU/RSS, диском PostgreSQL и числом соединений. При повторяющихся `503` уменьшайте стоимость работы или добавляйте ресурсы/вычислители после измерения.

## Границы масштабирования

Текущие очереди, защита повторной генерации аккаунта и ограничения входа хранятся в памяти каждого процесса. Несколько реплик разделяют данные в PostgreSQL, но не общую очередь/счётчики; перед горизонтальным масштабированием нужны общий limiter на прокси/Redis и, при существенном потоке расчётов, отдельная долговечная очередь заданий. Текущая генерация синхронна для клиента, поэтому не переживает перезапуск процесса. Фронтенд получает ошибку и предлагает повторить действие.

Новая миграция создаёт обычные индексы и кратковременно блокирует записи в соответствующие таблицы. Для уже большой действующей БД планируйте окно обслуживания либо отдельное согласованное создание индексов `CONCURRENTLY`; не запускайте нагрузочный тест на пользовательской БД. Миграция проверена на изолированных БД и затем применена при [релизе 29 сентября](RELEASE-20260929.md); нагрузочные цифры выше остаются результатом локального теста.

Основание для реализации: [Node.js worker threads](https://nodejs.org/api/worker_threads.html), [Node.js HTTP lifecycle](https://nodejs.org/api/http.html), [соединения Prisma 6](https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections).
