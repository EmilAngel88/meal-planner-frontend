# Обновления через GitHub

Репозиторий: <https://github.com/EmilAngel88/meal-planner-frontend>. Сборки видны во вкладке **Actions → CI / CD**. Основная ветка — `master`.

## Что выполняется автоматически

1. При отправке кода и в pull request проверяются стиль, типы, модульные тесты, интеграционные тесты с отдельным PostgreSQL, сборка и известные уязвимости зависимостей.
2. Собираются три Linux-образа: API, сайт и миграции. В отдельной тестовой базе проверяются запуск, регистрация, вход, отсутствие административных прав у нового пользователя и выключенные по умолчанию продажи.
3. Только успешная сборка основной ветки публикуется в GitHub Container Registry. Номер версии совпадает с коммитом; сервер получает образы по неизменяемому digest. В Actions сохраняется архив `release-<commit>` на 30 дней.
4. При включённом `DEPLOY_ENABLED` готовые образы отправляются на сервер. Сначала создаётся и проверяется резервная копия базы, затем применяются миграции и обновляется приложение. Проверяются контейнеры и публичный адрес здоровья API. Ошибка запуска возвращает прежние образы приложения; база автоматически не откатывается.

Проверки и контейнерные сборки работают без платёжных ключей и доступа к рабочей базе. Приём денег остаётся отдельной настройкой монетизации.

## Однократное подключение сервера

Серверу нужны Linux, Docker с Compose v2, `bash`, `flock`, `curl`, исходящий HTTPS к GitHub Container Registry и доступ по SSH от GitHub Actions. На существующей установке сохраняются `/opt/meal-planner/.env`, проект Compose `meal-planner` и том `meal-planner_postgres_data`. Файл `.env` не передаётся через GitHub. Для новой установки сначала подготовьте `.env` по [инструкции Docker](docker.md).

В **Settings → Environments** создайте окружение **production**. В **Settings → Secrets and variables → Actions → Variables** задайте:

| Переменная | Значение для текущей установки |
| --- | --- |
| `DEPLOY_ENABLED` | `false` до проверки доступа; `true` включает обновления |
| `DEPLOY_HOST` | адрес вашего сервера |
| `DEPLOY_USER` | отдельный пользователь развёртывания с доступом к Docker и каталогу приложения |
| `DEPLOY_PORT` | `22` или ваш порт SSH |
| `DEPLOY_PATH` | `/opt/meal-planner` |
| `DEPLOY_EDGE` | `true`, если используется внешний прокси через `docker/compose.edge.yml` |
| `DEPLOY_HEALTH_URL` | публичный HTTPS-адрес `/api/health` |

В окружении **production → Environment secrets** добавьте:

| Секрет | Содержание |
| --- | --- |
| `DEPLOY_SSH_KEY` | отдельный закрытый ключ для развёртывания; открытая часть должна быть в `authorized_keys` выбранного пользователя |
| `DEPLOY_KNOWN_HOSTS` | доверенная запись SSH-сервера из `known_hosts`; отпечаток предварительно сравните через консоль хостинга |

Не добавляйте личный SSH-ключ, пароли базы или ключи ЮKassa в репозиторий. Пользователь с доступом к Docker фактически имеет расширенные права на сервере; ключ должен предназначаться только для этого проекта. Настройка не создаёт публичный вход администратора по совпадению email.

GitHub сам выдаёт временный `GITHUB_TOKEN` для загрузки образов. На сервере данные входа хранятся в отдельном временном каталоге на время обновления и удаляются при завершении. Для приватных образов отдельный постоянный токен не нужен. При жёстком прерывании runner временный каталог `/tmp/meal-planner-auth-*` может остаться; его следует удалить, срок токена ограничен запуском GitHub Actions.

Для внешнего прокси сохраните в серверном `.env` правильные `PROXY_NETWORK`, `TRUST_PROXY`, `CORS_ORIGINS` и `NUXT_PUBLIC_API_BASE`. Существующий Caddy и соседние приложения не перезапускаются.

Когда значения готовы, включите `DEPLOY_ENABLED=true` и запустите **Actions → CI / CD → Run workflow → master**. Последующие отправки в `master` запускают всю цепочку автоматически. Настройки защиты ветки и обязательных проверок можно включить отдельно в GitHub.

## Если обновление завершилось ошибкой

- Ошибка проверок или сборки: сервер не изменяется. Откройте красный шаг в Actions.
- Ошибка получения образов или резервной копии: новое приложение не запускается.
- Ошибка миграции: прежние контейнеры приложения остаются работать. Проверьте состояние миграции перед повторной попыткой; ошибка SQL может требовать ручного исправления.
- Ошибка запуска или публичной проверки: предпринимается возврат прежних образов. Actions всё равно показывает ошибку; не считайте откат доказательством исправности базы.

Резервные копии лежат в `/opt/meal-planner/backups/pre-<release>.dump`, архивы версий — в `/opt/meal-planner/releases/`, ссылка `current-release` указывает на последний успешно запущенный выпуск. Копии не удаляются автоматически: следите за свободным местом и настройте их отправку за пределы сервера. Копия на том же диске не защищает от потери сервера.

Миграции следует делать совместимыми с предыдущей версией приложения. Автоматический откат образов не умеет отменять несовместимые изменения схемы и не восстанавливает базу поверх новых пользовательских данных. Для отката кода создайте отменяющий коммит через GitHub или `git revert` и проведите его через те же проверки. Не используйте `migrate reset` или `docker compose down -v` на рабочей установке.

## Локальная проверка механизма развёртывания

```sh
bash -n scripts/deploy-release.sh scripts/deploy-over-ssh.sh
node --test scripts/tests/deploy.test.mjs
```

Эти тесты проверяют остановку при ошибках скачивания, копирования базы и миграции, а также откат при отказе приложения или публичной проверки. Они используют подставные команды Docker и проверки доступности; настоящий запуск контейнеров отдельно проверяется в Actions.
